All notable versions of Portaless are documented in this file.
For the real, verified state of each module, always see [`ROADMAP.md`](./ROADMAP.md)
and [`AGENT.md`](./AGENT.md) — this changelog is the history of what was added in
each version, not a guarantee that everything listed is free of `TODO`s.

> **Versioning.** Up to `0.0.9.N` the project used an internal build counter with
> four components (`0.0.9.4`), which is not valid semver. From here the version
> is **valid semver** and the top released block is tagged, so an external
> security review or a second maintainer has a fixed point to check out. The
> first such tag is **`v0.0.10`** (the accumulated work that used to sit under
> the single `0.0.9.10 (unreleased)` heading). New work goes under **Unreleased**
> and gets its own tag when it ships. This is **not** called “Beta”: the ROADMAP
> gates that name on exit criteria that are still open.

## Migration (how to update a deployment without losing data)

Portaless versions are semver. **Before updating any deployment, check the data
contract and back up.** The core is fail-closed: a database newer than the code
refuses to start (it never degrades the schema silently).

| Deployment | Update |
|---|---|
| **Self-host / Docker** | `npm run doctor` (or `docker compose exec portaless npm run doctor`) → if the DB is behind, `npm run migrate` (backup first, into `<dataDir>/backups/`). Docker: pin the image tag, `docker compose pull && docker compose up -d`; the server migrates on boot after `applySchema`. Rollback = restore the backup and go back to the previous tag. |
| **Cloudflare Pages (D1)** | Deploy the new tag, apply the new schema (`wrangler d1 execute <DB> --remote --file=schema.sql`) and stamp the ledger (`node node_modules/tsx/dist/cli.mjs scripts/stamp-d1.mjs --out stamp.sql` → `wrangler d1 execute <DB> --remote --file=stamp.sql`). |
| **GitHub Pages (static)** | No database; update by merging the new tag (the `update-upstream` workflow opens a PR “Update to vX”). |

Rules: run `doctor` before `migrate`; never edit `schema_migrations` by hand; a
migration that fails rolls back its transaction and the boot aborts (the backup
is intact). `layoutVersion` on content and `engines.portaless` on plugin
manifests are the forward-compatibility guards (both fall back safely / fail
closed).

## Unreleased

- **ADR 0001 records the email configuration/transport decision and its remaining risks.** Keep generic `site_settings` + `plugin_email_quota`; keep `packages/email-transport` separate from auth `EmailSender`; email credential encryption at rest remains explicitly deferred. The ADR also records that tokens may currently be retained when a provider destination changes, `from` domain ownership is not verified, and delivery outcomes can be unknown after transport failures; these are open implementation/security items, not accepted guarantees.
- **MVP acceptance contract: private canonical node, public projections, client/resource constraints.** `docs/mvp/acceptance-contract.md` separates the local/Cloudum canonical node from Git-based public publishers; classifies secrets, private archive, drafts, approved revisions and public evidence; defines single-writer restore/handover and revision-bound reputation evidence; and records the 20 GB/2 GiB target as unverified until a workload fixture is measured. It distinguishes ChatGPT custom-MCP account/transport availability from OpenAI API-key compatibility, records that a free-account write flow is a blocker until tested, and specifies a one-row 320px mobile-header inventory that preserves 44px targets.
- **Architecture contract: private canonical node, approved public projections.** New `docs/architecture/canonical-node-and-public-projections.md` records the target local-or-Cloudum node, public Git projection, private archive/secret boundary, one-active-writer rule, revision evidence and restore/handover. It explicitly distinguishes the target from today's CLI publisher and records that Cloudum hosting, approval-bound publishing and private-archive isolation are not yet implemented. `deployment-engine.md` now points to this contract instead of implying self-host-only is the target.
- **Security/architecture review of the `email:send` + migrations work — ten fixes (R1–R10) plus a package extraction.** A self-review of the last ten commits found, among others, a **ship-blocker**: the migration gate returned `503` for every request on a healthy Cloudflare deployment (the operator applies `schema.sql` via wrangler and the ledger table never exists, so it read as "pending"); the gate now blocks only when the ledger exists and diverges, `scripts/stamp-d1.mjs` (`npm run stamp:d1`) stamps the D1 ledger, and a new end-to-end middleware test covers it (**R1**). The SMTP transport had **no tests** and two real defects: a plugin `data` value with CR/LF (interpolated into the template) could inject SMTP headers or terminate `DATA`, and a body line starting with `.` ended `DATA` early — both fixed (dot-stuffing + CR/LF stripping + `STARTTLS`-only-if-advertised, credentials refused over plaintext), plus a reply-reader bug that dropped multiline lines (**R2/R10**). `GET /admin/api/email` leaked the SMTP password / webhook token to **any** authenticated role — now admin-only and the credential is write-only (`hasCredential`, keep/replace/clear) (**R3**). The daily quota is refunded when the transport fails (**R4**), is **fail-closed** (refuses to send) without a persistent backend instead of using a per-isolate counter (**R5**), and the `plugin_email_quota` DDL lives in **one** place (**R6**). `isSafeEmailUrl` now blocks private/metadata hosts (**R7**), the gate no longer creates an empty DB file as a side effect (**R8**), and the 2-row mobile header is documented as an accepted trade-off (**R9**). The email config + transport moved to a neutral **`packages/email-transport`** (killing the inverted `plugin-sandbox → dashboard` dependency). Docs corrected: README/ROADMAP/plugin-author-guide/AGENT(S) now say **5** (not 6) backends answer `501` and `email:send` is real; ROADMAP archives the superseded "stays 501" decision; self-hosting gains an "Email transaccional" section. Verified: vitest 207 files / 1917 passed, build 71 pages, validate-manifests OK, doctor schema v4, `npx playwright test` 62/62.
- **`email:send` hardened: strict payload whitelist + the quota table moves into the numbered-migration ledger.** The capability already shipped in TASK 5 (blind delegation: the plugin sends `{ template, to, data }`, the core approves the template, injects the site `from` and enforces a per-plugin daily quota). - **Data contract: numbered forward migrations, a `doctor`, automatic backup and fail-closed startup.** Until now `schema.sql` was re-applied in full on every boot and each store self-migrated with scattered `ALTER TABLE … ADD COLUMN` — working, but with no record, order, backup or protection against a database *newer* than the code. - **Phase 13 (§13.1 + §13.2 + §13.3): element variants, an explicit size scale, and one spacing rhythm instead of hand-set pixels.** **Variants** on eight elements — `Hero` (centered/split/minimal, `split` takes a new `imageUrl`), `Heading` (plain/eyebrow/ruled), `Button` (solid/outline/ghost, each keeping AA contrast: solid uses ink on the light accent, outline and ghost use `--accent-text`), `Testimonial` (plain/quote/card), `ProductCard` (standard/compact/featured), `FAQ` (list/bordered/numbered), `Form` (stacked/inline), `Gallery` (grid/masonry, masonry via CSS `column-count`, no JS). The rule that keeps them from decaying: **a variant is a shape, not an ornament** — if two values differ only in colour or padding, that is what theme tokens are for. `Paragraph`, `Image`, `Columns`, `Spacer`, `Video`, `Map`, `SocialIcons`, `StoreBlock`, `LinkList` and `ProfileHeader` deliberately got none: the last three are identity elements whose real variation *is* the theme pack, and `Columns` deserves a `ratio` (60/40) which is a separate select, not a variant. **An unknown variant falls back to the default** (`variantOf()`), the same fail-safe as a theme pack that does not resolve: it lands on the known look instead of breaking the render on data that is not ours. **Size is its own field, not a variant**, because 3×3 = 9 options per element is an unmanageable panel. Only `Hero`, `Heading` and `Button` take it — the three where two instances on the *same* page may need different scales; in `ProductCard`, `Testimonial` or `Form` the size is the variant's job and duplicating it would be two ways of saying the same thing. **`Heading.size` is visual and `Heading.level` is semantic and they are never mixed**: an `h2` with `size: lg` is a large section heading, correct and accessible, and nobody ever moves up to `h1` for size — the comment says so in the type, because that is the kind of thing a contributor breaks six months later. **The rhythm lives in `global.css`, not in `DesignTokens`**, next to the existing `--radius-button`/`--radius-input` precedent: a theme pack controls *identity* (colour, radius, density), not rhythm, and putting `--space-*` in `DesignTokens` would force every pack to declare spacing and break the 16-variable parity `theme-pack.test.ts` fixes. `--space-unit` is the only real length; `--space-1..8` derive from it. Every atom emits `var(--space-N, <literal>px)` with a fallback that **equals the real step** — a lying fallback is a time bomb, and a test compares the `SPACE_STEPS` table against `global.css`. **`--density` stops being decorative**: it was a declared token with no consumer, and CSS cannot turn a word into a length, so `applyDesignTokens()` now derives `--space-unit` from it (comfortable 4px / compact 3px) — a compact skin now actually compacts. **The panel speaks human words**: `optionLabels` (additive, falls back to the raw value) labels all 9 variants *and* the pre-existing selects, which used to show `centered` or `h1` in a Spanish UI. `list_page_components` passes `editableProps` through wholesale, so the MCP surface got variants and labels **without touching the MCP** (`git status packages/mcp-server/` is empty). `Button.style` (`primary`/`secondary`) is still read so stored pages render identically, but it is no longer editable — `variant` replaces it. - **Open element catalog via element packs — a plugin can contribute its own elements without the core changing.** The catalog was closed by three simultaneous anchors, not one: `elementRegistry` (a plain, non-frozen object literal), the closed `ElementType` union, and `validateNode` rejecting any `node.type` not in the registry — plus the MCP parity test demanding registry == palette == schema enum. An `ElementPack` (`packages/atomic-elements/src/elements/element-pack.ts`) is a **declarative, data-only** contribution: `ContributedElement` carries a namespaced `type` (`demo.Badge`, `paywall.Boundary`), `displayName`, `icon`, `defaultProps`, `editableProps` (same shape as core), and a `render` that is **only** `kind: "html-template"` with a `template` the *host* interpolates and escapes — never a render function. That boundary is deliberate and comes from the repo's own `ProductGrid` precedent: the host holds the render function, the plugin supplies data, because a function does not cross an `isolated-vm` and the AST must stay JSON-serializable and deterministic. `validateElementPack(pack, coreTypes)` is pure (same style as the sandbox's `validateManifest`): it enforces namespacing, forbids shadowing a core type, rejects duplicates, and rejects any `render.kind` other than `html-template`. Packs persist in `ElementPackStore` (D1 → SQLite → in-memory, mirroring `page-store.ts` / `plugin-registry/store-factory.ts`, seeded-if-empty with a `demo-pack`), backed by a new `element_packs` table (`schema-additions/element-packs.sql`, `schema.sql` regenerated). `resolveCatalog(core, packs)` fuses them into a `ResolvedCatalog` (`lookup`/`has`/`allTypes`/`packTypes`/`palette`) that render, validation, the MCP and the editor all consume; a pack can never shadow a core type (defense in depth, though `validateElementPack` already rejects it at registration). **Render gained two modes and a structural secret guard**: `renderPage(layout, { mode, catalog, dynamicRenderer })` interpolates pack templates (escaped) in both modes, but a `requiresEdgeEval` node in `static` (build) mode emits a placeholder that receives **only `{type, nodeId}` and never touches `props`** — by construction there is no code path for a `secretProps` value to reach a static artifact — while `request` (runtime) mode lets the caller resolve it via `dynamicRenderer` at the edge. `validatePageLayout(layout, catalog?)` now takes an optional catalog (default: core, fully retro-compatible), and `PageStore` gained `setCatalog()` so `save()` accepts pack types when a catalog is wired (best-effort in `createPageStore`, falling back to core-only on any pack-load failure). **MCP resolves the catalog at call time** (packs are DB-backed and do not exist at import): `index.ts` resolves it once and passes it through `server.ts` to `list_page_components` (which now tags each entry `source: "core" | "pack"` and exposes `packTypes`; the render template is deliberately withheld as host data, not agent input) and to `create_page`/`update_page`/`insert_block`. The node schema's `type` accepts the core enum **or** any namespaced string, but that only validates *shape* — real **membership** is decided per-call by `checkNodeTypes`/`findUnknownTypes` against the resolved catalog, so an unknown dotted type gets an actionable error naming the offending types and pointing at `list_page_components`. **The editor's palette, canvas preview and property panel iterate the resolved catalog** instead of `elementRegistry` directly (a pack node is `undefined` in the registry and would have crashed): `GET /admin/api/element-packs` (admin-session-guarded, auto-routed by both Cloudflare Pages and the self-host runtime) returns the packs, `editor.astro` fuses them with the core already in the client bundle, and a pack element is edited with the *same* property panel (same `editableProps` shape) and previewed via `renderContributedTemplate` (exported from `render.ts`). A `demo.Badge` element proves the injection end-to-end, covered by 25 tests in `tests/unit/element-catalog-plugins.test.ts` (pack validation, catalog fusion, store loading with invalid packs ignored, page validation with/without catalog, static/request/placeholder rendering, MCP visibility and membership rejection, retro-compat without a catalog). **Honest limits**: (a) `requiresEdgeEval` is proven as a structural placeholder + the `request`/`dynamicRenderer` contract, but the end-to-end path *through the sandbox* (`runPluginInProduction` / the commerce `host-bridge` pattern) and the `secretProps` build-time guard are the explicitly deferred second pass; (b) there is no pack-installation UI — the store is seeded in memory/SQLite, and operator installation with consent (Permissions-Center style) is the missing operable piece; (c) packs do not sandbox code between themselves (each pack is validated data, not code in the catalog — plugin code still runs where it runs today, in `plugin-sandbox` with capability tokens); (d) the MCP `type` union widening is the one behavioral change to an existing contract — a namespaced string is now *schema-accepted* anywhere a block type appears, with catalog membership as the authority, so a dotted type no longer gets a Zod error but a domain error. - **Portaless Cloud Images: APW as cryptographic SSOT** (ROADMAP; `packages/cloud-images/` from zero — "C2PA without a central authority"): **Cloud Image v1 payload** (`v: 1`, `imageId`, `contentHash` = sha256 over the sidecar-free bytes, `contentType`, `byteLength`, `declaredOrigin` human|ai|mixed, `siteId`/`siteDid`, `signedAt` **inside** the signed data as a cryptographic existence timestamp, `keyAlgorithm: "ed25519"` preparing ML-DSA, contemporaneous public SiteTrustScore `trust` captured with `scoreSiteDimensions` + `projectTrustView` public-only — `null` and never blocking when the trust store is unreadable) and sidecar `{ payload, jws }` signed **server-side** with the site's active key (`signCloudImage` over `signSiteJws`: JCS RFC 8785 + Ed25519, `typ: apw-image+jws`; `verifyCloudImageSidecar` selects the key by `kid`, requires canonical-byte equality between the sidecar payload and the JWS payload — tamper-evident —, rejects a `kid` outside the payload's `siteDid`, and accepts legacy RFC 7638 thumbprint kids). Embedding in a PNG private **`pAPW`** chunk (spec 5.4 private/standard/safe-to-copy): `embedPng` inserts before IEND or replaces an existing chunk, `extractPng` verifies the CRC (corrupt = absent), `stripPng` returns the original bytes byte-for-byte — the hash is computed over those bytes and the image travels with its own signed metadata. New `cloud_images` store (D1/SQLite/InMemory + factory, `content_hash` UNIQUE so re-uploading the same bytes dedupes; DDL in `schema-additions/cloud-images.sql`, master `schema.sql` regenerated from 18 sources, `REQUIRED_TABLES` joined). ### Documented

- **Ecosystem boundaries: what Portaless OS owns, and what the Linstark repos own.** New [`docs/architecture/ecosystem-boundaries.md`](./docs/architecture/ecosystem-boundaries.md) draws the line between this repository and the commercial layer, so the group of repos stops describing the same boundary with different words. **In Portaless (AGPL, this repo):** the APW specification and resolver, LTP (SiteTrustScore, witnesses, calibration), Portaless Index, the kernel (element catalog, Permissions Center, plugin sandbox, auth, deploy engine, MCP server) and the content modules (Posts, Recents, Videos, Music, Shop read-only, Explore). **Outside it:** Linstark Cloudum (managed hosting), LinsWork (closed module), Tenantless (fleet orchestration) and Ecomless (inventory and invoicing) — none of which require a change to the core's license, because they are either operations, or code that runs **inside** the sandbox. Writing that third piece surfaced two more facts worth stating plainly. First: `@portaless/apw-resolver` **is** installable standalone today — the build bundles with `esbuild --bundle`, which inlines the six cross-package source imports, and `npm pack` + `npm i` into an empty project imports cleanly on both `.` and `./full`. What is missing is not the capability but the guarantee: no CI job packs and imports the tarball, so a new entry point or an incomplete `files:` could break it unnoticed. Since that package is the entry condition for a second APW implementer, it is recorded as needing an automated check rather than a manual one. Second: the "Top" ordering does **not** need a view counter, because the metric already exists and is the one Veraciers are judged by — `site_trust_community_votes` already stores a 1–5 score, a free-text comment and a timestamp per category and voter; `periodKey()` already buckets by day, ISO week and UTC month; and `bayesianScore` already computes a prior-weighted score (`NEUTRAL = 4.0`, `PRIOR_WEIGHT = 3`) on top of witness calibration and weighted consensus. Filters like `Top`, `Recents`, `Confidence`, `Old`, `New` and `History` become different readings of that one trust graph. What blocks it is narrower than "no metric exists": `voter_id` is minted in the browser as `anon-${crypto.randomUUID()}` in `localStorage`, so it is stable but trivially re-mintable and bounded only by `ip_hash`. Until a vote is bound to a signed `did:apw`, a public review history is a form anyone can refill — with it, every filter becomes reproducible by a third party from signed, chained attestations, which is the property neither X nor Google offers today.

- **R-05 in policies remains off, and the reason is data, not config (spec §6.5, ERRATA E-9)**: `policyDimensions["R-05"]` was left `false` after measurement, not by habit. A subject's R-05 is the calibration of the attestations **it** emitted (A.4.4), but `loadReaderConduct()` only loads what it **received** (drops `iss` equal to the reader's DID), so even a reader with three calibratable, agreeing emitters ends with `R-05 = { score: 4.0, count: 0, weightSum: 0 }`: with `min_r05_weight = 2.0` the policy would reject it and everyone else. Missing: (1) a flow where the reader emits attestations over subjects (today only anonymous community voting by IP, no DID) and (2) a corpus of other emitters on the same (subject, dimension) for A.4.4's leave-one-out consensus — indexes or witnesses (section 7). The blocker is anchored as a regression in `tests/unit/apw-reader-conduct-config.test.ts` (never enable the flag without solving that) and documented in spec §6.5 and §7 and ERRATA E-9.
- **The three `reader_conduct` categories of spec §6.4 still have no rule, blocked by data, not code**: `rate_respected` (R-02), `paid_as_agreed` (R-03) and `redistribution` (R-04) are not emitted because the ledger does not supply their datum. `LedgerConductInput` is literally what `log-writer.ts` writes (`requestsTotal`, `policyViolationsDetected`) and the middleware records `charged: false` on all four paths: `requests_charged` and `revenue_usd` never move, because with Cloudflare Pay Per Crawl (in-band) the origin returns 200 + `crawler-price` and settlement happens out-of-band. Emitting `paid_as_agreed` from there would be inventing the payment. Each one waits on its own prerequisite: a rate in the content policy with its counter, a settlement that reports the outcome, and witnesses or denunciation for what the origin cannot observe. Regression in `tests/unit/apw-reader-conduct-config.test.ts`, detail in `CONDUCT_RULES`, spec §6.4/§7 and ERRATA E-9.
