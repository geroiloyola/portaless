## v0.0.9.10 (unreleased)

### Added

- **MCP tool parity with the visual editor, and native page `status` (draft/published).** The content tools' Zod `type` enum is now derived from `elementRegistry` at import time instead of being hardcoded per tool, fixing a real drift bug: when `Video`/`FAQ`/`Testimonial`/`Form`/`Gallery` joined the catalog, `create_page`/`update_page` still accepted only the original 12 types, so an agent composing a valid `FAQ` block got a Zod error even though `elementRegistry` and `PageStore` already supported it. The shared `elementNodeSchema` now lives in `packages/mcp-server/src/tools/element-node-schema.ts` and is imported by every content tool, so a new `ElementType` is accepted everywhere without touching the MCP server. `list_page_components` returns the full catalog per type (`type`, `displayName`, `icon`, `defaultProps`, `editableProps`) instead of a bare name list, so an agent can propose valid props without guessing; `renderHTML`/`renderHTMLAsync` are deliberately omitted (site render functions, not agent data). Three new granular tools — `insert_block`, `update_block`, `delete_block` — mutate a single node by `nodeId` (insert also addresses a parent + index + optional column slot) instead of forcing `update_page` to replace the whole `root`; they share one pure `node-ops.ts` (immutable, `nodeId`-addressed, distinct from the editor's path-based mutable `editor/tree-ops.ts`), require `content:read` + `content:write`, audit through the existing ledger, and persist via `PageStore.save()` → `validatePageLayout`. Catalog parity is locked by `tests/unit/mcp-element-schema-parity.test.ts` (registry set == schema enum == palette; every registry type parses). `PageLayout` gained a native `status?: "draft" | "published"`, replacing the `-draft` slug-suffix hack: `create_page` marks drafts natively (clean slug), `update_page` promotes them, `validatePageLayout` rejects any other value, `/admin/api/pages` exposes it, and `/admin/pages` shows a status badge plus a *Publicar* button (load → set `status` → PUT). The publish filter (`deploy-engine/draft-filter`) now excludes **both** mechanisms — native `status: "draft"` and the legacy `-draft` slug — via the new `excludeDraftPages`, and `publish-site.mjs` loads the layouts before filtering so no draft is ever published by accident. **Breaking for MCP clients**: `create_page` with `draftMode: true` no longer appends `-draft` to the slug; it sets `status: "draft"` (the response now reports `status` instead of a suffixed slug). **Honest limits**: (a) the agent tools can still edit a published page directly — the approval gate is the human publish action, not a per-write draft lock; (b) legacy `-draft` pages keep their slug and are not migrated; (c) the runtime page server (`functions/paginas/[slug].js`) does not check `status`, so a draft is reachable by URL on hosts with functions — the gate is publish, not serve, same as before; (d) the live collaborative UX (in-canvas agent commands, "ghost" updates) is out of scope — it would be a new subsystem and would break the "every agent write is a draft until a human approves" principle in `docs/architecture/mcp-agents.md`.

- **Phase 6 (repo-executable part) — publication maturity: RSS feed, `llms.txt` from the database, first-party analytics, and a generic `site_settings` table.** The ordered pre-Beta plan (RSS → `llms.txt` from DB → analytics → editor/MCP polish → exit criterion → newsletters/ATproto → paywall as a plugin) is written down in ROADMAP.md as **Phase 6 — Publication maturity**, together with the two decisions that shaped it: paywall content must be **rendered at the edge at request time** (static premium bytes are public in the repo and in every deploy) and the billing provider belongs to a **plugin** with capability tokens, never to core — core's economy stays pay-per-crawl. RSS: `/rss.xml` (RSS 2.0 + Atom `self`) for published posts, built by the pure `src/lib/rss.ts` and announced from every page via `<link rel="alternate" type="application/rss+xml">` and from the `Optional` block of `llms.txt`; drafts stay out through the same `publishedPosts()` filter that `/blog`, the sitemap and `llms.txt` use. Honest limit: no `content:encoded` (the repo has no markdown→HTML renderer at build time, and adding one only for the feed is not worth the dependency). `llms.txt` from the database: new `functions/llms.txt.js` merges the pages stored in D1/SQLite (the same table the editor writes and `/paginas/[slug]` serves) into the build-time file as a `## Páginas del editor` section, deduplicated by slug by slug, and it **does not** merge when the content policy blocks `ai_input` — the build now emits an `<!-- portaless:ai-input-blocked -->` sentinel for exactly this; on pure static hosting (GitHub Pages) there is no function and the JSON-only build file is served, the same honest limit as `/paginas/[slug]`. Analytics: `/admin/analytics` configures Plausible, Cloudflare Web Analytics, umami or a custom `https://` script, stored in the new `site_settings` key/value table (D1 → SQLite → InMemory, same store pattern as `site_skin`, registered in `schema-additions/site-settings.sql` and regenerated into `schema.sql`); the public site reads it from `/api/analytics` at request time (`functions/api/analytics.js`), with `src/pages/api/analytics.ts` emitting a build-time no-op (or a `PORTALESS_ANALYTICS_*` env configuration) for static hosting, and `BaseLayout` always requests the asset the same way it requests `/api/site-skin`. **The admin never stores JavaScript**: only provider + site id + (for `custom`) an `https://` origin, validated on write *and* on read, and the `<script>` tag is built by Portaless from those three values. Tests: `rss.test.ts`, `llms-txt-db.test.ts` (merge + function runtime), `site-settings-store.test.ts`, `admin-analytics-endpoint.test.ts` and a new browser spec `llms-txt-db.spec.ts` (a page created from the editor appears in `/llms.txt` with no publish and no rebuild, on the real self-host runtime). 151 files / 1292 passing + 1 skipped, coverage 85.78/78.66/85.48/87.64. Honest limits: the sitemap still lists only the JSON pages (the same pattern in `functions/sitemap.xml.js` is the pending follow-up); AT Protocol is documented as a discovery channel for a future subscriber import, never a delivery channel — it does not deliver email.

- **UI modernization pass — editorial type, warm tokens, SVG icon system, radius by role.** Typography is now self-hosted and role-based: `public/fonts/` carries Fraunces Variable (display), Inter Variable (UI/body) and IBM Plex Mono (technical data), declared in the new `src/styles/fonts.css` with a `woff2-variations` + `woff2` double `src` and imported by `BaseLayout`, so every page — public, admin and editor — gets the same three families with no network font request. Headings use a `clamp()` scale with `-0.01em` tracking, and `code`/`kbd`/`samp`/`pre` (DIDs, hashes, TXT records, publish commands) are mono everywhere instead of by page-specific `ui-monospace` declarations. Structural depth and motion: `--shadow-sm`/`--shadow-md` are tinted with the official **ink** RGB (38, 28, 21) rather than a neutral SaaS gray, `--transition-fast` centralizes the 150 ms interaction timing, and `.card` now sits on `--panel-bg` with a hover lift — all of it switched off by a `prefers-reduced-motion` block (the two new keyframes, `.ae-drop-indicator` and the editor save status, carry their own). Radius by role: `--radius` (22 px) stays for surfaces, and new `--radius-button: 8px` / `--radius-input: 6px` replace the 999 px pills that were applied to real buttons across 36 admin/permissions rules — pills survive only on badges and switches, where they are meaningful. Icons: new `packages/atomic-elements/src/elements/icons.ts` holds 19 Lucide SVGs (ISC) inline with `stroke="currentColor"` plus `iconLabel()` (SVG + text node) and `iconOnly()` helpers, replacing the emoji element catalog in `registry.ts` and every render site in `editor-app.ts`/`property-panel.ts`; the same treatment landed on the Permissions Center subject markers (`plugin`/`agent`/`theme`/`settlement-provider`/`reader`), which were `🧩 🤖 🎨 💳 🛰️` and are now inline Lucide SVGs in `permission-center-ui.ts` and in the static demo `public/permissions/index.html`. Palette cleanup: ~161 cool-gray hexes (`#1a1d26`, `#262b38`, `#101218`, `#12141a`, `#1b1e27`, `#1c1f26`, …) across 16 files were replaced by official tokens, and the one ad-hoc near-black (`#0b0c0f`) by `#261C15`; the two self-contained pages `admin/settlement` and `admin/wizard/rotate-identity` now import `global.css` instead of shipping their own `system-ui`/`#1f6feb`/pill styles. **Tool chrome stays dark on purpose**: a single `:is(...)` block in `src/styles/global.css` pins the official dark palette — and re-declares the historical `--portaless-*` aliases, which otherwise resolve at `:root` and inherit the light values — to the identity panel, admin form panels, SiteTrustScore source sections, permission capability cards and the editor shell, whichever theme the site is using; `public/editor/index.html` mirrors it. This is what keeps the lime accent readable: as text on bone it measures 1.4:1, inside the tool chrome it measures 9.66:1. Every text pair added or moved was checked against WCAG AA twice — by math and in a real browser over 24 sampled elements — and lime-as-text now goes through `var(--accent-text)` (olive `#5A6B24` on light pages, lime inside tool chrome); the `/beta` warning card border uses `--warning-fg` and the hero rule `--accent-2`. Screenshots and the publish-cycle GIF were regenerated. Honest limits: the palette-locked borders (`--panel-border` / `--portaless-border`) sit at 1.28:1 and 1.41:1, below the 3:1 non-text minimum — inputs stay identifiable by their fill and label, but changing this would mean editing the locked official palette, so it is left as-is and recorded here;

- **Phase 5 (repo-executable part) — Index becomes a real aggregator: A.4.4-style weight calibration, inter-node sync, operator UI, non-technical guide, public Beta announcement.** Witness weight calibration: after every sync each witness with an observation at the consensus `seq` gains an agree/disagree counter; the effective weight used in the consensus is `base × (0.1 + 1.8 × (agree+1)/(agree+disagree+2))` (Laplace-smoothed, ~1.9 ceiling / ~0.1 floor, starts at 1.0 with no data, clamped to the 1000 max; witnesses without an observation at the consensus seq are never counted — no data, no punishment); the operator's base weight remains an editable multiplier, and the published document carries `weight`/`baseWeight`/`calibrationFactor` per observation so any reader can recompute. Inter-node synchronization: peer Index nodes are configured per node (new `witness_index_peers` table) and `POST /admin/api/index/sync-peers` pulls each peer's `/.well-known/apw-index.json` using it strictly as **discovery** of (subject, witnesses) — every discovered subject is re-synchronized with the exact same fail-closed pipeline as a manual sync (witness chain → anchored statements → signature → deterministic `jti`), so a malicious peer can only cause verification of real chains, never inject observations (capped at 50 subjects / 20 witnesses per peer per sync; self-peer rejected; `witnessesUsed` DIDs converted to hostnames). New admin endpoints `GET/POST /admin/api/index/peers` (list/add/remove, max 20, `400 self_peer`) join the sync surface, and a new operator UI at `/admin/witness-index` (subjects table, sync-subject form, peer management; linked from the dashboard nav) makes all of it operable without curl. Erratum **E-12** (informative, no normative change) documents that the two points §5.7/§7 marked "out of scope for this version" — calibration and inter-node sync — now exist in the reference implementation. For non-technical users: [`docs/primos-pasos.md`](./docs/primos-pasos.md) — "install your site in 10 minutes" in Spanish (voseo), Docker + browser only, reusing the Phase 1 screenshots/GIF, with an explicit honest-limits section (terminal step on GitHub-Pages publish, single maintainer, exit criterion not met); linked from the README and `docs/self-hosting.md`. Public Beta announcement: new static `/beta` page (official palette via tokens, live on the GitHub Pages demo) plus a README "Public Beta" section — demo as first impression, what's ready vs not, guide/ROADMAP/SECURITY links — and the README's stale "Portaless Index: design/spec stage only" rows corrected to the real shipped status. Tests: `apw-witness-index-phase5.test.ts` (calibration math + agreement recording + effective weights in consensus + peer discovery re-verification, with real Ed25519 material), `apw-index-peers-endpoints.test.ts` (peers CRUD auth/validation/self-peer + sync-peers happy/unreachable paths), new store cases for calibration counters and peer state across both backends (22 new tests; 147 files / 1242 passing at the end of the phase). Honest limits: inter-node sync is pull-on-demand (no scheduled gossip daemon yet); "a real network" still needs more than one real operator (Phase 4 dependency); wizard testing with 3–5 non-technical people and the exit criterion (an outside person installing unaided) require people outside this repository and remain open.

Build pipeline: `tsc -p tsconfig.build.json` (Bundler resolution, `emitDeclarationOnly`, with a documented `D1Database` shim for the server-only store types) + esbuild ESM bundle (`dist/standalone.js` verified loadable in plain Node, bundle grepped clean of store/SQL code). `LOG_SEQ_CONFLICT` moved from `attestation-log-store.ts` to `history-log.ts` (the store re-exports it) so `history-log.ts`'s store dependency is type-only and the standalone runtime graph stays clean. New [`docs/protocol-apw/STARTER-KIT.md`](./docs/protocol-apw/STARTER-KIT.md): language-agnostic, pseudocode-per-step guide (fingerprint → TXT → did.json → chain → JWS/JCS → scoring) for an implementer who has never seen this code, with acceptance criteria = vectors V-01/03/05/06/08/09 and an honest section on did:web Path A being **not yet fully specified** (the subject-mapping erratum is not published; until then `did:apw` and `did:web` subjects must be treated as distinct). ### Fixed

- **`/admin/permissions` returned raw JSON to browsers, hiding the whole Permissions Center.** `functions/admin/permissions/index.js` answered every `GET /admin/permissions` with the grant snapshot, and functions run before static assets on both self-host and Cloudflare Pages — so the real page `src/pages/admin/permissions.astro` (built into `dist/admin/permissions/index.html`) was unreachable for a human: opening the "Centro de Permisos" card from the dashboard showed the raw JSON, the exact class of bug already fixed for `/trust/:siteId`. Fixed with the same content negotiation: with `Accept: text/html` and an `env.ASSETS` binding the function serves the static shell via `env.ASSETS.fetch("/admin/permissions/")` (directory → `index.html`, same helper Cloudflare Pages and the Node runtime expose), while the page's own `fetch("/admin/permissions")` — `Accept: */*` — and any API client keep receiving the JSON snapshot; missing binding or missing shell falls back to JSON as before, and the session check still runs **before** negotiation so an unauthenticated browser gets the 401, never the shell. Covered by 5 new unit tests in `tests/unit/admin-permissions-role-check.test.ts` (HTML delegation, shell 404 fallback, no-`ASSETS` fallback, `Accept: */*` never delegates, 401-before-negotiation) and a new Playwright spec `tests/browser/permissions-center.spec.ts` asserting the page renders `h1.pc-page-title` + `.pc-capability` + the inline `stroke="currentColor"` subject SVG in a real browser while the API still answers JSON. Also fixed while there: the trust badge read `0.0(0 comentarios)` because `.pc-trust-summary` is `inline-flex`, so each child's anonymous line box ate the leading space of its `textContent` — the votes text now gets `margin-left: 4px` like the score.

- **Site footer claimed the wrong license.** The public footer (`src/components/Footer.astro`, and the same shell in `functions/paginas/[slug].js`) said "open source, licencia MIT" — Portaless is **AGPL-3.0** (see `LICENSE`); the link now also points at the actual repository instead of the GitHub root.
- **`/admin/editor` rendered without its editor chrome.** The visual editor's 3-column shell CSS (palette / canvas / properties panel, dark tool chrome with skin-responsive accents) lived only inline in the standalone demo `public/editor/index.html`; the real editor at `/admin/editor` (which mounts the actual `mountAtomicElementsEditor` with DB persistence) showed the palette and canvas as unstyled stacked document flow. The chrome styles were extracted to `packages/atomic-elements/src/editor/editor-styles.css` so both editors render identically.
- **Dark panels rendered dark-on-dark after the Phase 0 palette change.** The APW identity banner on the admin home and the SiteTrustScore source panels on `/trust/:siteId` keep their deliberate dark backgrounds (`#14161b`) but were inheriting the light theme's ink text (`#261C15`) since Phase 0, making titles and labels nearly unreadable; they now set their own light text colors (`#e7e9ee` / `#9aa1b2`), including the copy buttons inside the banner.
- **`/trust/:siteId` returned raw JSON to browsers.** The Trust Layer Function shadowed the UI page on self-host and Cloudflare Pages (functions run before static assets), and `getStaticPaths() = []` meant no HTML existed at all — the SiteTrustScore page had never been reachable by a human. Fixed with content negotiation in `functions/trust/[siteId].js`: `Accept: text/html` serves a single static shell (`src/pages/trust/index.astro`, renamed from `[siteId].astro`) via `env.ASSETS` while the browser URL stays `/trust/<siteId>` (the shell reads the siteId from the pathname); API clients and the page's own `fetch()` (`Accept: */*`) keep receiving the JSON snapshot. Covered by 4 new unit tests in `tests/unit/site-trust-public-verification.test.ts`.
- **Trust page rows and badges were unstyled.** The page's `st-*` CSS was in an Astro-scoped `<style>` block, but the real content is created with `document.createElement` at runtime and never receives the scope attribute — categories rendered as run-together plain text ("Cumplimiento GDPRSin declarar"). The style block is now `is:global`.

- **Phase 0.5 — Close the edit→publish cycle: saving now publishes.** New public function `functions/paginas/[slug].js` serves `/paginas/<slug>` dynamically from the `pages` table at request time (self-host Node runtime and Cloudflare Pages): when the slug exists in the DB the stored layout is rendered through the atomic-elements engine inside the standard page shell (official-palette tokens via the `/api/site-skin` stylesheet, canonical URL, basic JSON-LD); when the slug is missing or the stored layout is corrupt it falls back with `context.next()` to the static build in `dist/`, so nothing breaks on GitHub Pages — there, editing a page still requires `npm run publish` (the honest static-hosting limit; the dynamic route simply doesn't exist without a runtime). The editor's save button is now labeled **Publicar** and, after a successful save, shows a "Ver página pública ↗" link straight to the public URL — the full cycle (edit → publish → open the URL → see the change) closes in the browser with no terminal. New minimum page manager at `/admin/pages` (linked from the admin home): lists every page with its title, opens one in the editor on click, creates a new one, and deletes it behind a `confirm()` — backed by a new `DELETE /admin/pages/:slug` (same session + `canWrite` guard as the PUT; `404 {removed:false}` when there was nothing to delete) and the list endpoint `GET /admin/api/pages`, which now returns `pages: [{slug, title}]` alongside the original `slugs` array (the list moved from `/admin/pages` to `/admin/api/pages` because the Function would otherwise shadow the manager's own static HTML). `PageStore` gained `remove(slug)` implemented by the D1, SQLite, LocalStorage, and HTTP stores. ### Documented

- **R-05 in policies remains off, and the reason is data, not config (spec §6.5, ERRATA E-9)**: `policyDimensions["R-05"]` was left `false` after measurement, not by habit. A subject's R-05 is the calibration of the attestations **it** emitted (A.4.4), but `loadReaderConduct()` only loads what it **received** (drops `iss` equal to the reader's DID), so even a reader with three calibratable, agreeing emitters ends with `R-05 = { score: 4.0, count: 0, weightSum: 0 }`: with `min_r05_weight = 2.0` the policy would reject it and everyone else. Missing: (1) a flow where the reader emits attestations over subjects (today only anonymous community voting by IP, no DID) and (2) a corpus of other emitters on the same (subject, dimension) for A.4.4's leave-one-out consensus — indexes or witnesses (section 7). The blocker is anchored as a regression in `tests/unit/apw-reader-conduct-config.test.ts` (never enable the flag without solving that) and documented in spec §6.5 and §7 and ERRATA E-9.
- **The three `reader_conduct` categories of spec §6.4 still have no rule, blocked by data, not code**: `rate_respected` (R-02), `paid_as_agreed` (R-03) and `redistribution` (R-04) are not emitted because the ledger does not supply their datum. `LedgerConductInput` is literally what `log-writer.ts` writes (`requestsTotal`, `policyViolationsDetected`) and the middleware records `charged: false` on all four paths: `requests_charged` and `revenue_usd` never move, because with Cloudflare Pay Per Crawl (in-band) the origin returns 200 + `crawler-price` and settlement happens out-of-band. Emitting `paid_as_agreed` from there would be inventing the payment. Each one waits on its own prerequisite: a rate in the content policy with its counter, a settlement that reports the outcome, and witnesses or denunciation for what the origin cannot observe. Regression in `tests/unit/apw-reader-conduct-config.test.ts`, detail in `CONDUCT_RULES`, spec §6.4/§7 and ERRATA E-9.

### Notes for this version

- The four sandboxing adapters are skeletons with complete architecture, but without real integration against each provider's API (explicit `TODO`) — do not use as active sandboxing in production yet. Historical note (fixed in v0.0.6): the self-hosted `isolated-vm` adapter started running real code in the next version.
- `InMemoryPermissionStore` does not persist across deployments; for production use a real backend (Git, KV, SQLite). Historical note (fixed in v0.0.9.2): the Permissions Center has real end-to-end persistence since that version.
- The system is deliberately multi-provider: a site can run 100% self-hosted (isolated-vm) without depending on Cloudflare, Deno Deploy, or Fastly.
