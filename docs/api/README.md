# Portaless HTTP APIs — Integrator Guide

This directory documents every HTTP surface a third party can use to connect to **Protocol APW**, **Portaless**, and the **Portaless Index**. All docs in English; the Spanish archive of the repo's longer-form documentation lives in `*_es.md` files at the root.

> **Status**: alpha. Everything documented here is implemented and covered by tests in this repository, but has not yet been exercised against large-scale third-party production traffic. Report issues via GitHub issues.

## Surfaces at a glance

| Surface | Auth | Who it is for | Docs |
|---|---|---|---|
| `/.well-known/*` (7 endpoints) | None (public) | Any site, crawler, AI agent, index, or verifier | [`well-known.md`](./well-known.md) |
| `GET /trust/:siteId` | Optional Web Bot Auth | Readers of a site's trust data (subject to the site's read policy) | [`well-known.md`](./well-known.md#get-trustsiteid) |
| `GET /trust/atproto/:handle` | None (public) | Anyone wanting an AT Protocol handle's identity joined with Portaless reputation (optional APW ↔ AT bridge) | [`well-known.md`](./well-known.md#get-trustatprotohandle) |
| `/llms.txt`, `/blog/<id>.md`, `robots.txt`, `sitemap` | None (public) | AI crawlers | Generated by the site |
| `/admin/api/*` | Session cookie + role | The site's own administrators (and automation acting as them) | [`admin.md`](./admin.md) |

## Base URLs

Every endpoint is served by a Portaless deployment at its own domain. In examples below, `https://<site>` is the deployment's origin (for example `https://example.com`). Well-known paths are fixed by the APW specification; admin paths are fixed by the Portaless implementation.

## Authentication model (summary)

- **Public endpoints** (`/.well-known/*`, content routes): no authentication. They are designed to be fetchable by anyone; trust comes from *cryptographic verification*, not from access control.
- **Reader identity** (`GET /trust/:siteId` when the site has an active read policy): [Web Bot Auth](https://webbotauth.xyz) draft-03 (RFC 9421, Ed25519). The agent's `Signature-Agent` origin must resolve to a `did:apw:<domain>` whose key history verifies (spec §6.3). No signature → `401`; valid signature without APW identity → the policy's `on_fail`.
- **Admin endpoints**: an authenticated admin session (cookie) with role `admin`. Some sensitive endpoints additionally require step-up (password + TOTP); this is noted per endpoint in [`admin.md`](./admin.md).

## Verifying a site end to end (the 60-second recipe)

1. Fetch `https://<site>/.well-known/did.json` → the site's DID document (Ed25519 public key).
2. Resolve the DNS TXT `_apw.<site>` (or fetch the manifest from the well-known endpoints) → the `k` fingerprint. **Check**: RFC 7638 thumbprint of the `did.json` key == `k`. Mismatch → identity invalid (DNS wins; HTTPS cannot spoof it).
3. Fetch `https://<site>/.well-known/apw-log.json` → the chained attestation history (`keys` + `entries`). Verify each entry's JWS signature, consecutive `seq`, `prev` hashes, and that the TXT's `h` appears in the chain (spec §5.4, vectors V-05).
4. Fetch `https://<site>/.well-known/apw-attestations.json` → the full issuer JWSs referenced by the chain's `att` hashes. Cross-check completeness (every entry ↔ its JWS).
5. Optionally fetch `https://<witness>/.well-known/apw-witnesses.json` for each witness you trust, and re-run the §5.7 evaluation against the subject's chain (vectors V-13).
6. Optionally fetch `https://<index>/.well-known/apw-index.json` for a pre-computed directory — then **re-verify** any entry that matters against the raw chains (the index document is plain and deliberately re-verifiable; it carries no signature of its own).

Full normative rules: [`APW-SPEC-v1.3.md`](../protocol-apw/APW-SPEC-v1.3.md). Fixed test vectors for your implementation: [`APW-VECTORS-v1.3.md`](../protocol-apw/APW-VECTORS-v1.3.md).
